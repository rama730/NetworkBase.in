# M8 phase H-2 (branches) plan

> Native execution, test-first. Report Part H: H2, H6, H11, H14 (branch routes, `?branch=`), H24 and H26 rows for branches. It builds on H-1 (saves, `0096`). Deployed on its own with the user's go-ahead.

**Goal:** a workspace with History on can have branches. You create one from main or another branch, see its files and its changes against main, save on it, update it from main, and rename, delete or restore it. You can do this from the app, and from the CLI, which follows the git branch.

## Decisions (differences from the report's design)

1. **The app shows a branch in its own view; the main explorer stays on main.**
   - **Report (H2):** the picker switches the whole Files tab (tree, views, downloads, search) to the branch.
   - **Built:** the Files header's branch picker opens a branch page, with the coloured "On branch" bar and the branch in the address (`?tab=files&branch=<name>`). The page has:
     - its changes against main, with diffs
     - all its files
     - its saves
     - a zip download
     - editing a text file on the branch, and deleting one
   - **Why:** the explorer, previews, editor, links and locks are all keyed by main's file ids. Making each of them read branch content is the larger part of H-2's risk, and the branch page covers the H23 journey ("create, edit, save, see what's ahead").
   - **Later:** after merge requests, the explorer reads `?branch=` through the resolver.
2. **Writes on a branch go through Part G change sets that target the branch (`change_sets.branch_id`), applied by a branch writer.** This covers the CLI push on a branch, agents' change sets and the app's edit. There's no `files/place?branch=`: the CLI pushes on a branch through a change set it applies at once. The branch writer:
   - locks the branch row and checks the head the change started from (`BRANCH_MOVED`)
   - writes `branch_files` (only paths that differ from the branch's base)
   - records a save with its changes
   - **ponytail:** a file changed on the branch since the change set started is a conflict (`CHANGE_SET_CONFLICT`); it isn't merged as on main. Upgrade with merge requests.
3. **Update from main** does a three-way merge per path:
   - base: main at the branch's merge base
   - ours: the branch's own files
   - theirs: main now

   Paths changed only on main come in with the moved base. Paths changed on both sides merge text with `merge3`. Real conflicts are returned, and the call takes `resolutions: { path: "branch" | "main" }`. A merge editor comes with H-3.
4. **The CLI manifest on a branch** gives each file a revision number:
   - files unchanged from main keep main's version
   - the branch's own files get 1,000,000 + the save number that last changed them

   So the CLI's version-and-hash planner works unchanged. Its local state is kept per branch (`state.<branchId>.json`), and main keeps `state.json`.
5. **Migration 0097:**
   - `branch_files`
   - `change_sets.branch_id`
   - `save_changes.previous_content_hash`, with `op` re-made so a content change on a branch is a "change"

## Tasks

1. **0097 and the domain `src/lib/domain/branches.ts`:**
   - `validBranchName`
   - `listBranches` (ahead, behind, last save; filters mine, active, merged, stale)
   - `createBranch` (from main, or from a branch; checkpoint at the start; 500 active)
   - `renameBranch`, `deleteBranch` (30-day restore), `restoreBranch`
   - `branchTree` (the resolver), `writeBranch`, `updateFromMain`, `branchDiff`

   Tests: `tests/db/branches.test.ts` and `tests/unit/branch-names.test.ts`.
2. **Routes:**
   - `GET/POST /workspaces/:id/branches`
   - `PATCH/DELETE /branches/:b`, `POST /branches/:b/restore`, `POST /branches/:b/update`
   - `GET /branches/:b/files`, `/branches/:b/diff`, `/branches/:b/zip`
   - `GET /workspaces/:id/saves?branch=`
   - `manifest?branch=`, `extension/file?branch=` (read)
   - `POST /workspaces/:id/change-sets { branchId }`, with apply on a branch

   Plus the token rules.
3. **CLI:**
   - `nb branch list|create|switch|rename|delete|update`
   - git-following on every command that syncs: `.git/HEAD` is read with no git process; an unknown branch asks (`NEEDS_INPUT` with `--json`); a detached head refuses a push (`DETACHED_HEAD`)
   - `nb status` shows the branch
   - `nb push` and `nb pull` work on the branch
   - `nb log` on the branch

   Fake-server tests.
4. **App:**
   - the branch picker in the Files header (recent first, search, New branch, `b` opens it)
   - the branch bar and the branch page (changes, files, saves, edit, delete, update from main, zip)
   - the branch list (`?view=branches`)
   - browser tests, light and dark, 1440 and 390 px

Benchmark switching (the resolver) on 5,000 files; review and security check; gates; ledger; deploy with the go-ahead (0097); live check on ponytail with the CLI following a git branch.
